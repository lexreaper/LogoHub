# Лабораторная работа №1

## 12. Реализация базы данных

В рамках лабораторной работы №1 была реализована база данных информационной системы центра логопедии на основе схемы, разработанной в лабораторной работе №0.

Для хранения данных используется **PostgreSQL**, а взаимодействие Python-приложения с базой данных реализовано с помощью **SQLAlchemy ORM**.

В проекте реализованы ORM-модели:

- `User`;
- `Patient`;
- `SpeechTherapist`;
- `Specialization`;
- `SpeechTherapistSpecialization`;
- `Appointment`;
- `VisitRecord`.

Модель `SpeechTherapistSpecialization` представляет промежуточную сущность для реализации отношения многие-ко-многим между логопедами и специализациями.

Подключение к PostgreSQL выполняется посредством SQLAlchemy Engine и драйвера `psycopg2`. Для выполнения операций с базой данных используются сессии SQLAlchemy.

## 21. Запуск Nginx локально на Windows (дополнительное задание №1)

### 21.1. Настройка

Распакуйте Nginx, например в `C:\nginx`. В файле `C:\nginx\conf\nginx.conf` используйте конфигурацию (путь к проекту замените на свой):

```nginx
events { worker_connections 1024; }
http {
    server {
        listen 8080;
        server_name localhost;

        location /static/ {
            alias C:/Users/user/Desktop/techwp/nginx/static/;
        }

        location / {
            proxy_pass http://127.0.0.1:8000;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}
```

Для путей Windows внутри конфигурации Nginx используйте `/`, а не `\`. Важно: файл `nginx/nginx.conf` **внутри проекта** изначально настроен для Docker (`host.docker.internal`) и **не является** конфигурацией локально установленного Nginx, пока вы её не скопируете и не измените.

### 21.2. Запуск

Откройте **второе окно PowerShell**:

```powershell
cd C:\nginx
.\nginx.exe -t
.\nginx.exe
```

Nginx на Windows может запуститься без постоянного вывода в терминале — это нормально. Для изменения конфигурации:

```powershell
.\nginx.exe -t
.\nginx.exe -s reload
```

Для остановки:

```powershell
.\nginx.exe -s quit
```

Проверка в браузере:

| Адрес | Ожидаемый результат |
|---|---|
| `http://localhost:8080/docs` | Swagger UI через Nginx |
| `http://localhost:8080/health` | `{"status":"ok"}` через прокси |
| `http://localhost:8080/static/index.html` | Страница «Центр логопедии» от Nginx |

В заголовках HTTP-ответов через порт `8080` обычно виден `server: nginx/...`. Если `/docs` даёт 502 Bad Gateway, проверьте, что FastAPI действительно запущен на `8000` и в `proxy_pass` указан `127.0.0.1:8000`.

### 21.3. Альтернатива: Nginx в Docker Desktop

Если установлен Docker Desktop, можно **вместо** локального Nginx запустить из корня проекта:

```powershell
docker run --rm --name speech-nginx -p 8080:8080 -v "${PWD}/nginx/nginx.conf:/etc/nginx/nginx.conf:ro" -v "${PWD}/nginx/static:/usr/share/nginx/html:ro" nginx:alpine
```

Для этого варианта используйте конфигурацию проекта с `proxy_pass http://host.docker.internal:8000;`, а FastAPI запускайте с `--host 0.0.0.0 --port 8000`. Не запускайте два Nginx одновременно на порту `8080`.

## 22. Тестирование API через Swagger (дополнительное задание №2 — JWT)

Откройте **http://localhost:8080/docs**. Для любого запроса: разверните метод → **Try it out** → введите параметры и JSON → **Execute**. В разделе `Server response` смотрите фактический код и тело ответа. Примеры ответов `200` и `422` в нижней части Swagger — это **документация возможных ответов**, а не результат последнего запроса.

### 22.1. Регистрация пациента

`POST /auth/register`:

```json
{
  "email": "patient1@example.com",
  "password": "StrongPass123!",
  "full_name": "Иван Иванов",
  "birth_date": "2000-05-10",
  "phone": "+70000000000"
}
```

Ожидается `201 Created`, роль `patient`. На втором компьютере можно использовать тот же email, **если база другая**. При повторной регистрации в той же БД получите `409` — используйте существующего пациента либо другой email.

### 22.2. Вход пациента и проверка токена

`POST /auth/login`:

```json
{"email":"patient1@example.com","password":"StrongPass123!"}
```

Ожидается `200 OK` с `access_token` и `token_type: bearer`. Нажмите в Swagger **Authorize**, вставьте **сам токен** (обычно без слова `Bearer`) и подтвердите. Если до этого был токен другой роли, нажмите **Logout** и авторизуйтесь заново. Проверьте `GET /users/me`: ожидается `200`, роль `patient`.

Без токена защищённый метод возвращает `401 Unauthorized`. Не публикуйте токены на скриншотах целиком.

### 22.3. Чтение логопедов и специализаций

- `GET /therapists` — список логопедов;
- `GET /specializations` — список специализаций;
- `GET /therapists/{therapist_id}` — конкретный логопед;
- `GET /patients/me` — профиль текущего пациента.

Если список логопедов пуст, администратор должен создать логопеда по инструкции ниже. **ID могут различаться** на компьютерах и после пересоздания базы — используйте значения из реального ответа API.

### 22.4. Проверка ограничения прав пациента

Под JWT пациента вызовите `POST /specializations`:

```json
{"name":"Проверка прав пациента","description":"Тест разграничения доступа"}
```

Ожидается `403 Forbidden`, `{"detail":"Insufficient permissions"}`. Это **успешная проверка безопасности**, а не неисправность.

### 22.5. CREATE, READ, UPDATE записи на приём

Под пациентом вызовите `POST /appointments` с **существующим ID логопеда** (в нашем тесте был `6`, но на другом ПК он может отличаться):

```json
{
  "speech_therapist_id": 6,
  "appointment_at": "2026-11-20T14:00:00"
}
```

**Дата должна быть в будущем на момент тестирования**; если она уже прошла, замените её. У одного логопеда не может быть двух записей на одинаковое время. Ожидается `201 Created`, статус `scheduled`. Сохраните **фактический ID приёма** из ответа (в нашем тесте был `7`).

Вызовите `GET /appointments/{appointment_id}` — ожидается `200 OK`. Затем `PATCH /appointments/{appointment_id}`:

```json
{"status":"cancelled"}
```

Ожидается `200 OK`, статус `cancelled`. Пациент может **отменить**, но не физически удалить приём: `DELETE /appointments/{appointment_id}` под пациентом вернёт `403`. Для проверки удаления используйте администратора. **Не отменяйте приём, который хотите затем завершить логопедом**: для результата посещения создайте другой приём.

## 23. Создание тестового администратора и логопеда

### 23.1. Администратор

**Не пытайтесь зарегистрировать администратора через `/auth/register`**: публичная регистрация создаёт только пациентов. Создайте или настройте локального тестового администратора из корня проекта отдельной командой PowerShell. Этот скрипт не повышает роль чужого аккаунта и не удаляет записи:

```powershell
@'
from app.database import SessionLocal
from app.models.user import User
from app.security import hash_password

email = "admin@example.com"
with SessionLocal() as db:
    user = db.query(User).filter(User.email == email).first()
    if user is None:
        user = User(email=email, password_hash=hash_password("AdminTest2026!"), role="admin", full_name="Администратор центра")
        db.add(user)
        db.commit()
        print("Создан администратор:", email)
    elif user.role == "admin":
        user.password_hash = hash_password("AdminTest2026!")
        db.commit()
        print("Обновлён пароль администратора:", email)
    else:
        print("Email занят другой ролью; выберите другой адрес")
'@ | python -
```

Используйте `admin@example.com` — адрес с доменом `.local` (например, `admin@speech-center.local`) **не проходит** валидацию `EmailStr` на `/auth/login`. Пароль `AdminTest2026!` только для локальной проверки; замените его после демонстрации.

В Swagger выполните `POST /auth/login`:

```json
{"email":"admin@example.com","password":"AdminTest2026!"}
```

Замените токен в **Authorize**, проверьте `GET /users/me`: роль `admin`.

### 23.2. CRUD администратора

Под JWT администратора проверьте:

1. `POST /specializations` с `{"name":"Тестовая специализация","description":"Для ЛР2"}` → `201`, запомните `id`.
2. `GET /specializations/{spec_id}` → `200`.
3. `PATCH /specializations/{spec_id}` с `{"description":"Обновлённое описание"}` → `200`.
4. `DELETE /specializations/{spec_id}` → `204`, если специализация не используется логопедами.
5. `DELETE /appointments/{appointment_id}` → `204`, если у приёма **нет** результата посещения. Существующий результат посещения может привести к `409`.

Если логопедов ещё нет, создайте его через `POST /therapists`:

```json
{
  "email":"therapist1@example.com",
  "password":"TherapistTest2026!",
  "full_name":"Тестовый логопед",
  "description":"Специалист центра",
  "experience_years":5
}
```

Ожидается `201 Created`. Запомните `id` логопеда из ответа. Дополнительно можно проверить `PUT /therapists/{therapist_id}/specializations/{spec_id}` (назначение специализации) и `GET /therapists/{therapist_id}/specializations` (чтение связей). Для назначения используйте **существующую**, не удалённую специализацию.

### 23.3. Логопед

Если логопед создан через `POST /therapists`, используйте его email и пароль из запроса. Если логопед уже существует в БД после ЛР1, его старый `password_hash` может быть фиктивным; для **существующего логопеда** можно установить тестовый пароль, не создавая дубликат:

```powershell
@'
from app.database import SessionLocal
from app.models.user import User
from app.models.speech_therapist import SpeechTherapist
from app.security import hash_password

with SessionLocal() as db:
    therapist = db.query(SpeechTherapist).filter(SpeechTherapist.id == 6).first()
    if therapist is None:
        print("Логопед с ID 6 не найден — проверьте GET /therapists")
    else:
        user = db.get(User, therapist.user_id)
        if user is None or user.role != "speech_therapist":
            print("Связанный пользователь не найден или роль отличается")
        else:
            user.password_hash = hash_password("TherapistTest2026!")
            db.commit()
            print("Email логопеда:", user.email)
'@ | python -
```

Замените `6` на **реальный ID логопеда**. Для входа в `POST /auth/login` используйте email из вывода и пароль `TherapistTest2026!`. Авторизуйтесь его токеном и проверьте `GET /users/me` → роль `speech_therapist`.

### 23.4. Сценарий результата посещения

1. **Пациент:** войдите с JWT пациента, создайте **новый приём в будущем** у нужного логопеда через `POST /appointments`. Запомните ID приёма. Не отменяйте его.
2. **Логопед:** войдите со своим JWT. `GET /appointments` должен показать назначенный ему приём.
3. **Логопед:** `PATCH /appointments/{appointment_id}`:

   ```json
   {"status":"completed"}
   ```

   Ожидается `200`, статус `completed`.
4. **Логопед:** `POST /visit-records`:

   ```json
   {
     "appointment_id": 8,
     "description": "Первичная консультация",
     "result": "Проведена диагностика речи",
     "recommendations": "Выполнять упражнения ежедневно"
   }
   ```

   **Замените `8` на ID только что завершённого приёма.** Ожидается `201`. Если приём ещё не завершён — `409`; если он относится к другому логопеду — `403`.
5. `GET /visit-records` и `GET /visit-records/{record_id}` → чтение; `PATCH /visit-records/{record_id}` с `{"recommendations":"Обновлённые рекомендации"}` → изменение результата.
6. **Логопед:** `POST /specializations` → `403 Forbidden`, подтверждение ограничения административных прав.
7. **Пациент:** войдите обратно, `GET /visit-records` должен показать результат его приёма.

## 24. Примеры PowerShell без Swagger

В **третьем** PowerShell (FastAPI и Nginx продолжают работать):

```powershell
$login = @{email='patient1@example.com'; password='StrongPass123!'} | ConvertTo-Json
$token = (Invoke-RestMethod -Method Post -Uri http://localhost:8080/auth/login -ContentType 'application/json' -Body $login).access_token
Invoke-RestMethod -Uri http://localhost:8080/users/me -Headers @{Authorization="Bearer $token"}
Invoke-RestMethod -Uri http://localhost:8080/therapists
```

Для передачи русских строк при POST используйте UTF-8 байты:

```powershell
$body = @{name='Проверка прав'; description='Тест'} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri http://localhost:8080/specializations -ContentType 'application/json' -Headers @{Authorization="Bearer $token"} -Body ([Text.Encoding]::UTF8.GetBytes($body))
```

С токеном пациента здесь **ожидается `403`**. Старый Windows PowerShell иногда некорректно отображает русские символы в ответе; в Swagger они могут отображаться правильно.

## 25. HTTP-коды, ошибки и решения

| Код / проблема | Причина и действия |
|---|---|
| `200 OK` | Чтение или изменение выполнено |
| `201 Created` | Объект создан |
| `204 No Content` | Удаление/операция выполнена, тело ответа пустое |
| `400 Bad Request` | Например, время приёма в прошлом |
| `401 Unauthorized` | JWT отсутствует, неверен, истёк или вход не выполнен; заново войдите и обновите **Authorize** |
| `403 Forbidden` | У роли недостаточно прав или объект принадлежит другому пользователю |
| `404 Not Found` | Запись с таким ID отсутствует; проверьте фактический ID |
| `409 Conflict` | Повторный email, занятое время приёма, завершённый/отменённый приём или конфликт с результатом |
| `422 Validation Error` | Некорректный JSON или поле; email должен иметь допустимый домен, не `.local` |
| `500 Internal Server Error` при входе | Проверьте `JWT_SECRET_KEY` (длина не меньше 32) и traceback в окне Uvicorn |
| `502 Bad Gateway` от Nginx | FastAPI не запущен или неправильный `proxy_pass` |
| `ImportError` в `init_db.py` | Импортируйте класс `SpeechTherapistSpecialization`, а не старое имя таблицы |
| `UniqueViolation users_email_key` | Email уже занят; не переименовывайте другой аккаунт в существующий адрес |
| `GET /sw.js` или `/favicon.ico` → `404` | Необязательные файлы браузера, не мешают API |

**Замечание по времени:** API сохраняет дату приёма без часового пояса. Для локального теста используйте единый согласованный формат времени и проверяйте, что выбранная дата в будущем. Не используйте этот подход без доработки для распределённого production-приложения в разных часовых поясах.

## 26. Быстрый запуск в следующий раз

Если всё уже установлено, достаточно:

1. Убедиться, что служба PostgreSQL запущена.
2. **PowerShell №1:** перейти в проект, задать `$env:JWT_SECRET_KEY`, запустить `python -m uvicorn app.main:app --reload --port 8000`.
3. **PowerShell №2:** перейти в `C:\nginx`, при необходимости выполнить `.\nginx.exe -t`, затем `.\nginx.exe` (если Nginx ещё не запущен).
4. Открыть `http://localhost:8080/docs` и `http://localhost:8080/static/index.html`.
5. В Swagger выполнить `POST /auth/login`, обновить токен через **Authorize** и работать с API.

Остановка: `Ctrl + C` в окне Uvicorn; для Nginx `cd C:\nginx; .\nginx.exe -s quit`. PostgreSQL можно оставить запущенным.

## 27. Что показывать на защите ЛР2

1. Объяснить архитектуру **Nginx → FastAPI → SQLAlchemy → PostgreSQL** и разделение DTO (`Pydantic`) / ORM (`SQLAlchemy`).
2. Открыть `localhost:8080/docs`, затем `localhost:8080/static/index.html` — проксирование и статика.
3. `POST /auth/register`, `POST /auth/login`, `GET /users/me` — регистрация, JWT, идентификация.
4. `POST /specializations` под пациентом → `403` — разграничение ролей.
5. `POST /appointments` → `201`, `GET /appointments/{id}` → `200`, `PATCH /appointments/{id}` → `200`.
6. `DELETE /appointments/{id}` под пациентом → `403`, под администратором → `204` (для приёма без результата).
7. Под логопедом: `GET /appointments`, завершение приёма через `PATCH`, `POST /visit-records`, просмотр/редактирование результатов.
8. Показать PostgreSQL (таблицы и записи), объяснить ORM, внешние ключи, связь M:N, хеширование паролей, срок действия JWT.

**Ограничения ЛР2:** здесь реализованы REST API, Pydantic DTO, DI FastAPI, JWT и Nginx. gRPC, RabbitMQ и прочие технологии последующих работ не требуются для демонстрации этой лабораторной.

## 28. Командная работа

- Оба участника получают **один и тот же исходный код** из Git или ZIP; на каждом компьютере выполняют разделы 19–21.
- **Базы данных раздельные**, поэтому ID пациентов, логопедов, приёмов и специализаций могут не совпадать. Никогда не рассчитывайте, что `id=6` или `id=7` существует у напарника.
- Не добавляйте в Git реальные пароли БД, `JWT_SECRET_KEY`, токены, виртуальное окружение `.venv`, дампы БД с персональными данными.
- Для демонстрации используйте тестовые имена и адреса. Не запускайте `test_db.py` на базе, где есть нужные записи.
- Перед сдачей оба участника должны самостоятельно проверить `/health`, `/docs`, `/static/index.html`, регистрацию, JWT, CRUD и разграничение ролей.
